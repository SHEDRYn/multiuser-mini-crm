# Архитектура проекта Mini CRM API

## Обзор

Проект построен по принципам чистой архитектуры с разделением на слои (layered architecture). Каждый слой имеет свою ответственность и зависит только от нижележащих слоёв.

## Слои архитектуры

```
┌─────────────────────────────────────┐
│         API Layer (FastAPI)         │  ← HTTP endpoints, роутинг
├─────────────────────────────────────┤
│       Service Layer (Business)      │  ← Бизнес-логика, правила
├─────────────────────────────────────┤
│    Repository Layer (Data Access)   │  ← Абстракция над БД
├─────────────────────────────────────┤
│      Model Layer (SQLAlchemy)       │  ← ORM модели
└─────────────────────────────────────┘
```

### 1. API Layer (`app/api/`)

**Ответственность:**
- Обработка HTTP запросов и ответов
- Валидация входных данных через Pydantic схемы
- Маршрутизация запросов
- Обработка ошибок и возврат правильных HTTP статусов

**Компоненты:**
- `deps.py` - зависимости FastAPI (аутентификация, получение текущего пользователя)
- `v1/` - версионированные API endpoints
  - `auth.py` - регистрация и вход
  - `organizations.py` - управление организациями
  - `contacts.py` - управление контактами
  - `deals.py` - управление сделками
  - `tasks.py` - управление задачами
  - `analytics.py` - аналитика и отчёты

**Принципы:**
- Не содержит бизнес-логики
- Использует Pydantic схемы для валидации
- Делегирует работу Service Layer

### 2. Service Layer (`app/services/`)

**Ответственность:**
- Реализация бизнес-логики
- Проверка бизнес-правил
- Координация работы репозиториев
- Транзакционная логика

**Компоненты:**
- `auth.py` - аутентификация и регистрация
- `permissions.py` - проверка прав доступа (RBAC)
- `organization.py` - логика организаций
- `contact.py` - логика контактов
- `deal.py` - логика сделок с бизнес-правилами
- `task.py` - логика задач
- `activity.py` - логика активностей (timeline)
- `analytics.py` - аналитика

**Бизнес-правила:**
- Проверка прав доступа на основе ролей
- Валидация переходов стадий сделок
- Запрет удаления контактов с активными сделками
- Автоматическое создание активностей при изменении статусов
- Проверка сумм сделок при закрытии как "выигранных"

### 3. Repository Layer (`app/repositories/`)

**Ответственность:**
- Абстракция над базой данных
- CRUD операции
- Сложные запросы и фильтрация
- Агрегации для аналитики

**Компоненты:**
- `base.py` - базовый репозиторий с общими методами
- Специализированные репозитории для каждой модели

**Принципы:**
- Не содержит бизнес-логики
- Возвращает модели или None
- Инкапсулирует SQL запросы

### 4. Model Layer (`app/models/`)

**Ответственность:**
- ORM модели SQLAlchemy
- Определение структуры таблиц
- Связи между таблицами

**Модели:**
- `User` - пользователи системы
- `Organization` - организации (компании)
- `OrganizationMember` - связь пользователей с организациями + роли
- `Contact` - контакты
- `Deal` - сделки
- `Task` - задачи по сделкам
- `Activity` - таймлайн событий по сделкам

## Multi-tenant архитектура

Проект поддерживает multi-tenant на уровне организаций:

1. **Изоляция данных**: Каждая организация имеет свои данные
2. **Контекст запроса**: Каждый API запрос выполняется в контексте организации (заголовок `X-Organization-Id`)
3. **Проверка доступа**: Middleware проверяет, что пользователь имеет доступ к запрашиваемой организации
4. **Фильтрация**: Все запросы автоматически фильтруются по `organization_id`

## Система ролей (RBAC)

### Роли:
1. **owner** - владелец организации
   - Полный доступ ко всем ресурсам
   - Управление настройками организации
   
2. **admin** - администратор
   - Полный доступ ко всем ресурсам
   - Управление настройками организации
   - Может откатывать стадии сделок
   
3. **manager** - менеджер
   - Управление всеми сущностями (контакты, сделки, задачи)
   - Не может изменять настройки организации
   - Не может откатывать стадии сделок
   
4. **member** - участник
   - Просмотр всех ресурсов
   - Редактирование только своих ресурсов
   - Не может откатывать стадии сделок

### Реализация:
- `PermissionService` проверяет права доступа
- Проверки выполняются в Service Layer
- API Layer получает информацию о membership через dependencies

## Безопасность

### JWT аутентификация:
- Access token (30 минут)
- Refresh token (7 дней)
- Хранение в заголовке `Authorization: Bearer <token>`

### Хеширование паролей:
- Bcrypt через passlib
- Соль генерируется автоматически

### Валидация:
- Pydantic схемы на уровне API
- Бизнес-правила в Service Layer
- Проверка прав доступа перед каждой операцией

## База данных

### Технологии:
- PostgreSQL 14+
- SQLAlchemy 2.0 (async)
- Alembic для миграций

### Индексы:
- Primary keys на всех таблицах
- Foreign keys для связей
- Индексы на часто используемых полях (email, organization_id, status, stage)

### Миграции:
```bash
# Создать миграцию
alembic revision --autogenerate -m "описание"

# Применить миграции
alembic upgrade head

# Откатить миграцию
alembic downgrade -1
```

## Аналитика

### Эндпоинты:
1. `/analytics/deals/summary` - сводка по сделкам
   - Количество по статусам
   - Суммы по статусам
   - Средняя сумма выигранных
   - Новые сделки за период

2. `/analytics/deals/funnel` - воронка продаж
   - Распределение по стадиям
   - Конверсия между стадиями
   - Статусы внутри каждой стадии

## Тестирование

### Структура тестов:
```
tests/
├── unit/              # Unit тесты
│   └── test_services/ # Тесты бизнес-логики
└── integration/       # Integration тесты
    └── test_api/      # Тесты API endpoints
```

### Типы тестов:
1. **Unit тесты** - тестируют изолированные компоненты (сервисы, утилиты)
2. **Integration тесты** - тестируют API endpoints с реальной БД

### Запуск:
```bash
# Все тесты
pytest

# С покрытием
pytest --cov=app --cov-report=html

# Только unit
pytest tests/unit/

# Только integration
pytest tests/integration/
```

## Масштабирование

### Горизонтальное масштабирование:
- Stateless API (можно запустить несколько инстансов)
- JWT токены не требуют серверного хранилища
- Database connection pooling

### Кеширование:
- In-memory кеш для статических данных
- Можно заменить на Redis при необходимости

### Производительность:
- Async/await для неблокирующих операций
- Индексы на часто запрашиваемых полях
- Пагинация для больших списков
- Lazy loading для связанных объектов

## Мониторинг и логирование

### Health check:
- `GET /health` - проверка работоспособности API

### Логирование:
- Стандартный logging Python
- Можно интегрировать с ELK, Sentry

### Метрики:
- Можно добавить Prometheus metrics
- Отслеживание времени выполнения запросов

## Развертывание

### Docker:
```bash
docker-compose up --build
```

### Production:
- Использовать `.env` с production настройками
- Использовать HTTPS
- Настроить мониторинг
- Настроить backup БД
